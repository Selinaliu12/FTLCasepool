# FTL 競賽池 設計規格 v5.0

2026-09-26 · Selina（產品負責人）

本文件取代《FTL 競賽池 產品需求文件 v4.0》，內容為 v4.0 審查後逐題確認的結果。審查時沒有討論、由設計者先訂的做法，集中列在第 11 節，可以再調整。

---

## 1. 產品定位

FTL 競賽池是金融科技創新實驗室（社團）的內部工具，約 6 組、40 人使用。

它是一個**學期中的專案追蹤工具**，附帶一面**競賽布告欄**：

1. **追蹤進度**：各組交雙週進度、點燈號，系統依日期自動判燈，幹部一頁看出哪組需要幫忙。
2. **審核里程碑**：專案與比賽的每個階段都留下版本、評語與完成日。
3. **整理競賽**：幹部把比賽整理成卡片，組別把比賽掛到自己的專案。
4. **期末交出去**：管理員下載整學期資料，放進社團 Google 雲端硬碟保存。系統本身不做歷屆瀏覽頁面。

**設計原則**

- 燈號只回答「現在要不要去幫這組」；長期表現由「準時率」回答。
- 幹部的待辦（待審核）和學生的狀態（燈號）分開呈現，互不影響。
- 學生清楚知道自己的資料誰看得到，並留下「已了解」紀錄。
- 零件越少越好，方便沒有程式背景的下一屆接手。

## 2. 名詞

| 名詞 | 意思 |
| --- | --- |
| 學期 | 系統的基本單位。每學期重新匯入名單、設定時程，期末匯出 |
| 組 | 一個專案團隊。一人在同一學期只屬於一組 |
| 線 | 一組要被追蹤的一條進度。每組固定有 1 條「專案線」，每報名一場比賽多 1 條「比賽線」 |
| 交付項目 | 有截止日、需要繳交的東西：雙週進度、專案里程碑（M1–M3）、比賽階段 |
| 燈號 | 每條線的當前狀態：綠、黃、紅 |
| 準時率 | 一條線到目前為止，準時交出的交付項目比例 |
| 鎖定 | 上傳滿 2 小時後，檔案不能再刪除 |

## 4. 功能

### 4.1 登入與名單

- 以學校 Google 帳號（@g.nccu.edu.tw）登入，系統不保管密碼。
- 管理員每學期上傳名單 CSV，欄位：email、姓名、角色、組別、專案名稱。
- 登入時依 email 比對當學期名單，自動歸組。不在名單上的帳號看到「你不在本學期名單中，請聯絡幹部」，無法進入。
- 學期中換組、退出，由管理員手動調整。換組前的紀錄留在原組。
- 管理員指定每位專案幹部負責的組別。

### 4.2 第一次登入說明頁

每學期第一次登入時顯示，按「我已了解」才能繼續。系統記錄是誰、什麼時間按的。內容：

1. 學期中，你的進度內容只有自己組員、專案幹部和系統管理員看得到。其他幹部只看得到燈號與階段。
2. 期末資料會匯出到社團雲端硬碟，只有幹部看得到。
3. 系統管理員維護時技術上碰得到所有資料。
4. 上傳後 2 小時內可以刪除重傳，之後鎖定、永久保存。替換檔案後，繳交時間以新檔案為準。
5. 只收 PDF，每份最大 20MB。

### 4.3 上傳規則（所有交付項目共用）

- 只收 PDF，每份最大 20MB。
- 上傳後 2 小時內，該組任何組員都可以刪除檔案，或撤回整份繳交。刪除後不留紀錄、不算版本。
- 滿 2 小時自動鎖定，之後不能刪除或修改。
- **繳交時間 = 最後留下那份的上傳時間。** 上傳頁面固定顯示：「⚠️ 替換檔案後，繳交時間以新檔案為準。」
- 需要審核的繳交（里程碑、比賽階段），鎖定後才送到專案幹部手上、才寄送審通知。

### 4.4 雙週進度與中間週燈號

- **雙週進度**：組內任一組員填一份表單：
  - 燈號：綠／黃／紅
  - 三句話：這兩週做了什麼、卡在哪裡、接下來要做什麼
  - 上傳 PDF（表單上列出建議內容，彈性不強制）
- **中間週**：只點一下燈號。點紅燈必須補一句卡在哪裡。
- 每筆紀錄顯示是誰、何時填的。
- 截止後仍可補交，系統標記逾期天數。
- 里程碑所在的那一期，里程碑繳交取代當期雙週進度。
- 雙週進度與中間週燈號只屬於專案線。

### 4.5 燈號規則

每條線各自一個燈號，**只看當前狀態**。

**組員回報燈**（只有專案線有）：最近一次雙週進度或中間週點的燈號。

**系統判定燈**（每條線都有）：看這條線目前有沒有欠著的東西。

| 狀況 | 系統判定 |
| --- | --- |
| 有交付項目已過截止時間、還沒交，逾期未滿 3 天（72 小時） | 黃 |
| 有交付項目已過截止時間、還沒交，逾期滿 3 天以上 | 紅 |
| 有里程碑或比賽階段被退回、還沒重交 | 黃 |
| 以上都沒有 | 綠 |

**顯示燈** = 組員回報燈與系統判定燈中較嚴重的，並標示來源（「組員回報」或「系統：M2 逾期 2 天」）。

- 補交或重交送出後立即重新判定。逾期紀錄保留在歷程裡，並反映在準時率。
- 「連續兩次黃燈轉紅燈」不採用。
- 逾期天數門檻（1–3 天、超過 3 天）是管理員可調的設定值。
- 逾期時間從截止時間起算，時區為台北時間。

**準時率**（每條線）= 已到期的交付項目中，繳交時間在截止時間之前的比例。被退回後的重交不影響準時與否，只看第一次送出的時間。

### 4.6 幹部總覽看板

- 每組一張卡片，列出：
  - 每條線的燈號與來源
  - 目前階段、下一個截止日（剩幾天）
  - 各條線的準時率
- 排序：有紅燈的組排最前，其次黃燈，再來綠燈。
- 專案幹部另有一個「**待你審核**」清單，列出負責組別已鎖定、等待審核的繳交，以及已經等了幾天。

### 4.7 專案里程碑

- 每學期由管理員設定三個里程碑的日期與必交內容。日期由產品負責人依學期行事曆提供。
- 預設必交內容：
  - **M1 題目定案**：題目一句話、痛點描述、目標使用者
  - **M2 企劃初稿**：企劃初稿 PDF、MVP 雛型（截圖整理成 PDF 或填連結）、預計參加的比賽
  - **M3 期末成果**：最終企劃書 PDF、簡報 PDF、一段學期回顧反思
- 審核流程：
  1. 必交項目沒填齊，無法送出。
  2. 送出後 2 小時內可以撤回；鎖定後送到負責的專案幹部。
  3. 專案幹部按「通過」或「退回」並寫評語；退回必須填原因。
  4. 退回後重交的每一版都保留，算進「交了幾版」。
  5. **完成日 = 最後通過那一版的送出日。**

### 4.8 競賽大廳

- 所有幹部都可以新增競賽，第一版為**手動填寫**。
- 卡片欄位：名稱、主辦單位、主題、參賽資格、參賽人數、獎金或獎項、官方連結、報名截止日、繳件截止日、決賽日期。
- 所有人都可以瀏覽。預設依報名截止日由近到遠排列，卡片顯示剩餘天數。已過報名截止日的比賽，自動移到「已截止」區。
- **AI 整理（晚一週上線）**：幹部貼上網址，系統把網頁文字交給 AI 預填表單，幹部檢查、修改後發布。AI 讀不到的網站（需要登入、內容是圖片）就維持手動填寫。
- 不做重複偵測。

### 4.9 比賽線

- 組別從競賽大廳把比賽掛到自己的專案，可以掛 0 到多場。
- 掛上後勾選實際參賽成員，並按「確認報名」。確認後才產生比賽線，並通知負責的專案幹部。
- 比賽線固定三個階段，日期直接取自競賽卡片：

| 階段 | 截止日 | 上傳 |
| --- | --- | --- |
| 報名 | 報名截止日 | 報名成功證明 PDF |
| 繳件 | 繳件截止日 | 送出的作品 PDF |
| 決賽 | 決賽日期 | 決賽簡報 PDF |

- 每個階段都要上傳並經專案幹部審核，流程同 4.7。
- 狀態：準備中 → 已報名 → 已繳件 → 晉級／得獎／未入選。前兩段跟著階段通過自動前進；比賽結果由組員手動填寫。
- 與專案里程碑撞期時，兩邊都要照常繳交。
- 幹部修改卡片上的日期時，已產生的比賽線截止日跟著更新。

### 4.10 Email 通知

由社團 Google 帳號的 Gmail 寄出。每個事件只寄一次。

| 事件 | 收件人 |
| --- | --- |
| 比賽階段截止前 3 天 | 該組全體組員 |
| 任一條線轉為黃燈 | 該組＋負責的專案幹部 |
| 任一條線轉為紅燈 | 該組＋負責的專案幹部 |
| 里程碑或比賽階段送審（鎖定後） | 負責的專案幹部 |
| 送審後 2 天還沒審 | 負責的專案幹部 |
| 通過或退回（附評語） | 該組全體組員 |
| 組別確認報名比賽 | 負責的專案幹部 |

不寄的通知：雙週進度與專案里程碑的截止前提醒（由幹部在社團群組提醒），以及新競賽發布。

### 4.11 期末匯出

- 管理員按「下載整學期資料」，得到一個壓縮檔：
  - 每組一個資料夾，內分「專案」與各場比賽子資料夾，放所有保留下來的 PDF 版本。
  - 每組一份 `時間軸摘要.csv`（可用 Google 試算表開啟）：每筆繳交的日期、是誰交的、燈號變化、審核結果與評語。
  - 一份全社 `總表.csv`：每組每條線的各階段完成日、交了幾版、準時率。
- 管理員自己把壓縮檔放進社團雲端硬碟；雲端硬碟的共用設定決定誰看得到。
- 匯出後，管理員可以選擇：
  - **設為唯讀**：學期資料只剩管理員看得到，不能再修改。
  - **刪除**：成功下載過壓縮檔後才會出現這個選項，必須輸入學期名稱（例如「115-1」）確認。
- 下學期專案可以註記「延續自某個專案」（只是文字註記）。

## 5. 資料的樣子（白話）

系統要記住的東西，彼此的關係如下：

```
學期 ─┬─ 名單（人、角色、所屬組）── 「我已了解」紀錄
      ├─ 組 ─┬─ 專案線 ─┬─ 雙週進度／中間週燈號
      │      │          └─ 里程碑 M1–M3 ── 各版繳交 ── 審核與評語
      │      └─ 比賽線（每場一條）── 報名／繳件／決賽 ── 各版繳交 ── 審核與評語
      ├─ 競賽卡片
      └─ 通知寄送紀錄
```

PDF 檔案本身放在檔案倉庫，資料庫只記「哪一份檔案、誰、什麼時候上傳」。

## 6. 技術架構與費用

所有服務以**社團共用 Google 帳號**註冊，交接時只需移交這個帳號。

| 項目 | 服務 | 用途 | 每月費用 |
| --- | --- | --- | --- |
| 網站 | Next.js，部署於 Vercel 免費方案 | 網站畫面與後端邏輯 | 0 元（限非商業用途） |
| 資料庫與登入 | Supabase 免費方案 | 名單、繳交紀錄、燈號、Google 登入、定時工作 | 0 元 |
| PDF 儲存 | Cloudflare R2（免費 10GB） | 所有上傳檔案 | 0 元（需綁卡） |
| 寄信 | 社團 Gmail | 通知信 | 0 元 |
| AI 整理競賽 | Claude API | 貼網址預填卡片 | 儲值最低 5 美元，可用數學期 |

**定時工作**（由 Supabase 的排程每 15 分鐘執行一次）：鎖定滿 2 小時的上傳、送出送審通知、重新判定燈號並寄轉燈通知、截止前提醒、催審提醒。

**選 Supabase 而不選 Firebase 的原因**：資料彼此關聯（人—組—線—階段—版本），用表格最自然；後台像試算表，方便不懂程式的人接手；Firebase 存檔案與定時工作都必須升級付費方案，也沒有花費上限。

**注意事項**

- Supabase 免費專案約一週無人使用會暫停：設定免費的定時喚醒。
- 上線前確認 Supabase 免費方案的備份方式；如果不能自行下載，就另設定期匯出。
- Gmail 每日寄送有上限，以 40 人的規模估算足夠。
- 價格為 2026 年 9 月的公開方案，開通前再確認一次。

## 7. 上線批次

實際日期要等學期行事曆確定後再定案。批次 3 必須在 M2 截止前上線。

| 批次 | 目標 | 內容 |
| --- | --- | --- |
| 1 | 2026-10-02 | 登入、名單分組、第一次登入說明頁、雙週進度與中間週燈號、上傳規則、燈號規則、幹部看板 |
| 2 | 約 10-09 | 競賽大廳（手動填寫）、掛比賽、確認報名、比賽線 |
| 3 | M2 截止前 | 專案里程碑與比賽階段審核、「待你審核」清單、email 通知 |
| 4 | 批次 3 後一週 | AI 貼網址整理競賽 |
| 5 | 期末前 | 期末匯出、設為唯讀、刪除 |

- 每批上線前，先請 1 組試用一輪。
- 系統上線前已發生的進度與 M1，先用現有方式收件，之後由管理員補登，並把補登的繳交時間設成實際繳交時間。

## 8. 成功指標

| 指標 | 目標 | 衡量方式 |
| --- | --- | --- |
| 雙週進度準時繳交率 | 80% 以上 | 系統自動統計 |
| 歷程完整度 | 每組 M1–M3 與各次雙週進度齊全 | 期末匯出時檢查 |
| 競賽資訊對報名有幫助 | 問卷平均 4 分以上（滿分 5，目標待確認） | 期末問卷 |

## 9. 不做的範圍

- AI 模擬評審、AI 評分
- 自動爬蟲
- 社團資源庫
- Discord 通知
- 重複競賽偵測
- 對外公開與相關同意機制
- 平台內的歷屆歸檔瀏覽
- 雙週進度與專案里程碑的截止前提醒信
- 專案跨學期直接延續（只保留「延續自」註記）

## 10. 風險

| 風險 | 因應方式 |
| --- | --- |
| 比賽與專案里程碑撞期，負擔加重 | 觀察準時率；低於 80% 時考慮讓比賽繳件抵當期進度 |
| 雙週進度沒有提醒信，準時率偏低 | 幹部在群組提醒；第一個月準時率偏低就加提醒信 |
| 第一批只有 6 天開發時間 | 第一批只放必要功能；先請 1 組試用 |
